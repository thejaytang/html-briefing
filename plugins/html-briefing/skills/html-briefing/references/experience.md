# Lessons distilled from real briefing iterations

These rules originated in repeated technical-work briefings. They preserve observed failure patterns while removing business data, internal paths, specific products and individual contribution claims. They are design experience, not a benchmark or a claim of universal effectiveness.

| Repeated failure | Transferable rule | Check |
|---|---|---|
| Audience reaches implementation before understanding the task | Introduce role, workflow, obstacle and consequence before the core design | A new reader can explain why the solution exists |
| Tool lists and notes compete with the mechanism | Give each scene a theme and main visual; bind details to objects | The default view contains the actual solution |
| Arrows are mistaken for narrative continuity | Preserve object identity through state changes | The audience can track the same input into output |
| A control merely adds cards or changes color | Connect action to evidence, operation and output | Switching the same case exposes the substantive difference |
| Closing a parent leaves stale details | Model ownership and clear descendant states | Repeated selection and parent collapse leave no orphan explanation |
| Fixed pane widths make the main visual too small | Allow boundary resizing and supporting-pane collapse/restore | Narrow previews retain a clear restore control and usable content |
| Language changes reset the current learning context | Confirm up to three languages before design; use a top-right segmented switch | Switching preserves valid selection, expansion, search and pane state |
| Viewing controls are scattered or stale after Escape | Group language and fullscreen/exit in the top right | Actual fullscreen state updates the same visible control |
| Dense technical labels disappear on projection | Use contrast, legible typography and responsive space | Inspect wide, narrow and short windows at real size |
| Flow lines move away from their fields | Recompute anchors in one coordinate system | Resize and expansion keep connections attached |
| Test counters hide the method's value | Put method, observed result and allowed conclusion together | A count cannot substitute for test evidence |
| A screenshot is treated as motion verification | Observe transitions and rapid/reverse interactions | Dynamic behavior has actual evidence |
| Development success is called portable delivery | Verify a moved/extracted final package offline | Unavailable target platforms remain untested |
| Project-specific assumptions become universal | Extract the failure and response, not the original business story | New scenes use their own facts and contribution boundaries |

## Defaults users can override

A useful title pattern is “short phrase: conclusion or theme,” with a one-sentence explanatory subtitle. A chapter sidebar may help long presenter-led briefings. Object-bound disclosure usually keeps technical details readable. Loops can help repeatable mechanisms. None of these prescribes language, brand, chapter count, Roman numerals, glass effects, fixed canvas, sidebar layout or animation on every scene.

Store project overrides in the project's existing instructions/design source. Do not alter installed third-party skills to express project preferences. User and project requirements govern the workflow.

The optional [editorial glass preset](editorial-glass.md) captures a requested combination of large serif titles, an accented phrase, vertically overlapping translucent pages and release-to-snap navigation. Use its parts when they fit the brief. Preserve readable overflow and stable controls, and verify native gestures before claiming smoothness. This is a reusable design choice, not a replacement for continuous reading in other projects.

## Maintenance

Change rules in response to reproducible failures or a demonstrated recurring need. Preserve stable rules here and keep release/evaluation evidence in the repository's project-support area. Do not add a gate, template or file for every incidental comment.

## Flow canvas default

New presentations default to [flow canvas](flow-canvas.md). This is a presentation/navigation model, not a fixed page-size or card-style requirement. Chapter titles form the leftmost vertical column and content unfolds to their right. A focused page fills the stage; deliberate content-node centering is retained through zoom. Keep view changes independent from disclosure and reading memory.
