# Matching Sites delivery in ChatGPT

For authorized **create/revise work in ChatGPT**, make a matching Site alongside the HTML deliverable by default. First establish the actual host and available Sites capabilities; a conversation reference, URL or skill file alone does not establish ChatGPT hosting support. Follow explicit local-only, offline-only, draft-only or do-not-publish instructions. Discussion, review and environment-only tasks do not create or publish a Site.

1. Keep one canonical content and implementation source. Build the local HTML and hosted output from it; synchronize subsequent authorized edits rather than maintaining a separate hand-written copy.
2. Read the available Sites building and hosting skills at the point of use. Reuse an existing project identity and Site URL; do not register a duplicate. Keep the user's existing audience, with private access as the default for a new Site. Native approvals and permissions remain in force.
3. Verify the relevant HTML flows, then use the native Sites publishing workflow. Publish only approved briefing material and required assets, preserving licensing. Exclude source-project private files, credentials, logs and unrelated history.
4. A successful native deployment result with its literal URL is the hosted-delivery evidence. A local preview, saved archive or version alone is not publication. Report local HTML verification and Sites publication separately.
5. Deliver both the local artifact and the matching Site link. If Sites is unavailable, blocked or publication fails, finish the independent HTML work and state the specific missing synchronization step. Do not claim a successful sync or silently select another hosting provider.

Outside ChatGPT, keep the established local HTML delivery default. Add Sites when the user requests it or the project already specifies that delivery. Sites is a host capability, not redistributed source in this plugin, and this rule does not authorize changing an audience or sending material to other people.

A hosted version does not establish offline operation, native Windows acceptance or other-host compatibility. Keep those checks tied to the actual deliverable and tested environment.
